## 1 项目概述

### 1.1 一句话定义

守药人是一个**面向基层医疗场景的 AI Native 用药安全 Agent**：把老人手里「一袋说不清楚的药」变成结构化清单，自主调用 8 个工具完成相互作用核查、按肾功能与年龄分层、循证检索取证，输出一份可直接执行的用药重整与随访方案，并把每一步判断做成可点击、可回溯、可审计的轨迹。

### 1.2 问题定义

中国 60 岁及以上人口已超过 3 亿，基层慢病随访名单中「多重用药」（≥5 种）是常态。可预防的用药伤害有三类典型形态：

| 形态 | 真实例子（本作品演示数据 p-001） |
| --- | --- |
| **组合错误** | 华法林 + 阿司匹林（自行加服）+ 布洛芬（村卫生室自购）→ 消化道出血风险升高 2–3 倍 |
| **剂量没跟着器官功能走** | eGFR 42 mL/min/1.73m² 仍在用常规剂量二甲双胍；78 岁仍在用长效磺脲类格列本脲 |
| **症状被当成「老了正常」** | 牙龈出血、大便发黑被归因为「上火」，实际是 INR 3.8 的抗凝过度 |

**责任主体缺失**：村卫生室通常只有 1–2 名村医，既看病又随访；县级医院药师难以覆盖到村；基层几乎不存在「用药重整」这一动作。这不是模型能力问题，而是**服务供给问题**。

### 1.3 解决路径

```
采集（多模态） → 核查（确定性规则） → 取证（混合检索） → 出方案（Agent 编排） → 守门（安全层） → 留痕（审计/回放）
```

设计上刻意做了一个反直觉选择：**把「判断」交给确定性代码，把「表达与规划」交给大模型。**
理由是医疗场景的容错率极低——「二甲双胍在 eGFR < 30 时禁用」这条规则不需要模型来推理，它需要的是永远不出错、永远可复现、永远能指出来源。模型的用武之地在于：理解老人含糊的口语、决定该查什么、把结论翻译成家属能执行的话。

### 1.4 与同类产品的差异

| 维度 | 常见「用药助手」 | 守药人 |
| --- | --- | --- |
| 交互 | 关键词检索说明书 | 自然语言 / 语音 / 拍照，多模态入口 |
| 判断 | 单药信息展示 | 两两相互作用 + 器官功能分层 + 年龄不适当用药 |
| 依据 | 无出处 | 每条结论带 `[n]` 引用，可点开原文与打分明细 |
| 过程 | 黑盒 | 7 步轨迹 + 工具入参返回 + SSE 实时可视化 |
| 责任 | 免责声明 | 11 条红旗症状强制转诊 + 输出改写 + JSONL 审计 |
| 可复现 | 依赖云服务 | 无 Key 走本地规则引擎，克隆即可运行 |

## 2 需求分析

### 2.1 用户画像

| 角色 | 场景 | 核心诉求 | 设计约束 |
| --- | --- | --- | --- |
| **村医 / 社区护士**（主用户） | 随访日，老人带着一袋药来 | 5 分钟内判断「这堆药有没有问题、下一步做什么」 | 输出必须是可执行动作，不是科普长文 |
| **患者家属**（协同用户） | 周末回村，替父母整理药 | 知道「哪些药要停、什么时候复查、什么情况打 120」 | 口语化、可直接复制到微信 |
| **老人本人**（受限用户） | 看不清、不会打字 | 用嘴问、听语音播报 | 大字号、语音输入输出、慢速播报 |
| **评审 / 监管视角** | 判断系统是否可信 | 能否追溯每一次判断的依据 | 全链路留痕与回放 |

### 2.2 功能需求

| 编号 | 需求 | 实现位置 |
| --- | --- | --- |
| F1 | 患者档案与用药清单可视化，区分医嘱药/自购药 | `components/console/PatientRail.tsx` |
| F2 | 自然语言提问，流式回答 | `app/api/chat/route.ts` + `lib/store/useConsoleStore.ts` |
| F3 | 药物两两相互作用核查（21 条规则） | `lib/tools/index.ts::check_interaction` |
| F4 | 按 eGFR/血钾/INR/血红蛋白/年龄分层（14 条临床规则） | `lib/tools/index.ts::assessLabs` |
| F5 | 循证检索 + 引用追溯 | `lib/rag/index.ts` |
| F6 | 用药重整五段式方案 + 复查节点 | `build_med_plan` / `buildPlan` |

| F12 | 能力外化为 MCP 工具 | `mcp/server.mjs` + `app/api/mcp/route.ts` |

### 2.3 非功能需求

- **可靠性**：任何一级外部依赖失效都必须有降级路径，不得出现空白回答。
- **可解释性**：任一结论可追溯到知识库片段；任一运行可回放。
- **性能**：首屏无阻塞请求；检索 < 50ms；流式首 token < 1.5s（规则引擎 < 200ms）。
- **隐私**：PII 在进入模型前脱敏；不收集真实患者数据；日志本地留存。
- **可访问性**：键盘可达、焦点可见、`aria-live`、尊重 `prefers-reduced-motion`。

## 3 系统架构设计

### 3.1 分层架构

```
┌── 表现层（React 19 / App Router）───────────────────────────────────────────┐
│ 落地页 · 智能诊台三栏 · 冲突图谱(SVG) · 轨迹回放 · 安全审计 · 架构页(实时检索演示) │
│ 状态：Zustand 会话机（useConsoleStore）· 渲染：MiniMarkdown（引用徽标）          │
└───────────────────────────┬──────────────────────────────────────────────┘
                            │ POST /api/chat → text/event-stream（自定义事件协议）
┌── 编排层（Node Runtime）────▼──────────────────────────────────────────────┐
│ Agent 运行时（lib/agent/runtime.ts）                                          │
│ 输入安全审查 → 规划 → 工具编排 → 证据锚定 → 生成 → 输出守门 → 落盘             │
└──┬────────────────┬─────────────────┬──────────────────┬───────────────────┘
   │                │                 │                  │
┌──▼──────┐  ┌──────▼──────┐  ┌───────▼──────┐  ┌────────▼─────────┐
│ 工具层   │  │ 检索层       │  │ 安全层        │  │ LLM 抽象层        │
│ 8 tools │  │ BM25+向量+RRF│  │ 4 道闸门+审计  │  │ OpenAI 兼容协议   │
└──┬──────┘  └──────┬──────┘  └──────────────┘  └──────────────────┘
   │                │
┌──▼────────────────▼─────────────────────────────────────────────────────────┐
│ 数据层：data/kb/*.md（17）· drugs.json（29）· interactions.json（21）· redflags.json（11）· patients.json（4）│
└─────────────────────────────────────────────────────────────────────────────┘
                            ▲
                 mcp/server.mjs（stdio）→ /api/mcp（工具实现唯一一份）
```

### 3.2 一次提问的数据流

```
1. 浏览器 POST /api/chat {patientId, question}
2. 运行时 screenInput()：PII 脱敏 + 红旗症状匹配
      └→ 命中 emergency：level=block，forceReferral=true
3. 规划：LLM（JSON 计划）或规则引擎（固定 7 步）
      └→ emit plan（前端立即画出 7 个待执行节点）
4. 逐步执行工具：每步 emit step(running) → tool_call(args) → tool_result(summary, ms)
      └→ search_kb 额外 emit retrieval(query, hits)
5. lab_assess 产出高风险发现 → 证据锚定：对未覆盖的 evidence docId 定向检索
      └→ emit retrieval（定向取证）
6. 生成：LLM 流式 token 或规则引擎按标点切片
      └→ emit token × N（前端增量渲染）
7. guardOutput()：诊断断言改写 / 绝对化拦截 / 剂量无引用拦截
      └→ emit safety（若有改写）
8. verifyCitations() → 置信度 → emit answer_meta → 保存 run + audit → emit done
```

### 3.3 自定义 SSE 事件协议

之所以不用通用 SDK 的 data-stream，是因为本作品需要把「过程」暴露给用户：

| 事件 | 载荷 | 前端行为 |
| --- | --- | --- |
| `run_start` | runId, patientId, mode, model | 初始化 live 状态 |
| `plan` | steps[] | 渲染步骤清单（此时全部 pending） |
| `step` | stepId, status, detail | 更新单步状态图标与说明 |
| `tool_call` | id, name, args | 追加工具卡片（显示入参） |
| `tool_result` | id, status, ms, summary, data | 回填耗时与摘要，可展开 data |
| `retrieval` | query, hits[]（含四项打分） | 证据面板追加证据 |
| `token` | text | 追加到当前 assistant 消息 |
| `safety` | level, flags[], forceReferral | 顶部红色横幅 + 轨迹中的守门记录 |
| `answer_meta` | citations[], confidence | 回答底部显示「引用 N 条 · 置信度」 |
| `note` | text, level | 系统说明（如降级提示） |
| `done` | runId, durationMs, usage | 结束态，开放「查看决策轨迹」链接 |

协议实现见 `app/api/chat/route.ts`（服务端 ReadableStream）与 `lib/store/useConsoleStore.ts`（客户端帧解析 + reducer）。

### 3.4 状态管理策略

| 状态类型 | 存放位置 | 理由 |
| --- | --- | --- |
| 患者主数据（档案/用药/相互作用） | 服务端组件一次下发 | 切换患者零请求，避免闪烁 |
| 会话消息 / 运行轨迹 / 当前标签页 | Zustand（`useConsoleStore`） | 跨组件共享，事件驱动更新，避免层层 props |
| 大字模式 / 主题 | `localStorage` + `html[data-*]` | 全局 CSS 变量驱动，不走 React 重渲染 |
| 运行轨迹持久化 | `logs/runs/*.json` | 服务重启后仍可回放（评审答辩需要） |

## 4 AI 技术方案

> 本章对应评分表最高权重项（35%），重点阐述**选型理由、集成方式、优化策略**。

### 4.1 大模型选型与集成（8%）

**选型**：抽象为 OpenAI 兼容协议（`/chat/completions`），内置 `deepseek` / `zhipu` / `qwen` / `openai` 预设，`custom` 可接任意兼容网关。

理由：
1. **可替换性**：比赛现场网络不可控，能在 4 家供应商之间一键切换是工程刚需；国产模型（DeepSeek/GLM/Qwen）成本低、中文医疗语料更充分。
2. **零锁定**：不写任何厂商私有字段，评委换成自己的 key 也能跑。
3. **视觉能力**：`VISION_MODEL` 单独配置（如 GLM-4V / Qwen-VL），用于药盒识别。

**Prompt 工程**（`lib/llm/prompts.ts`）：
- 系统提示固定五段输出结构（一句话结论 / 风险清单 / 现在要做的 3 件事 / 需要医生决定的事 / 什么时候必须就医），压缩自由发挥空间；
- 强制引用格式 `[n]`，`n` 来自给定证据片段；证据不足时必须写「现有资料不足以判断」；
- 剂量只给方向不给数值（「由执业医师核定」），从源头降低越权风险；
- 规划阶段要求**只输出 JSON**（`response_format: json_object`），运行时做防御式解析（`normalizeLlmPlan`：抽取 `{...}`、校验工具名、步数不足则回退、强制补安全审查步）。

**优化策略：双引擎**

| 引擎 | 触发条件 | 能力 | 价值 |
| --- | --- | --- | --- |
| LLM | 配置了 key | 自主规划、自由表达 | 应对口语化、模糊提问 |
| 规则 | 无 key / 网络失败 / 输出不合格 | 固定 7 步 + 模板合成 | 演示不翻车；作为 LLM 对照基线 |

两引擎共用工具层、检索层、安全层，**只替换「规划」和「表达」两个环节**，因此切换不改变产品行为契约。这既是容错设计，也让「模型到底带来了什么增量」变得可测量。

温度固定 0.2（`LLM_TEMPERATURE`），医疗场景优先稳定性而非多样性。

### 4.2 Agent / 工作流设计（8%）

**7 步规划**（`mockPlan` / LLM 生成，最终统一为 `PlanStep[]`）：

| 步 | 标题 | 工具 | 设计意图 |
| --- | --- | --- | --- |
| s1 | 载入患者档案与用药清单 | `get_patient` | 建立事实基线 |
| s2 | 两两核查药物相互作用 | `check_interaction` | 组合风险 |
| s3 | 按检验指标做风险分层 | `lab_assess` | 器官功能匹配 |
| s4 | 检索循证依据并锚定证据 | `search_kb` | 提供可引用依据 |
| s5 | 生成用药重整与随访方案 | `build_med_plan` | 转化为动作 |
| s6 | 转诊单 / 家属通知 | `make_referral` / `notify_family` | 分支决策 |
| s7 | 安全审查与输出守门 | —（纯推理） | 强制质量闸 |

**自主性体现在三处**：

1. **意图驱动分支**：命中红旗症状时 s6 走 `make_referral`（并前置「立即就医」），否则走 `notify_family`。
2. **证据驱动的补检索（证据锚定）**：`lab_assess` 返回的风险发现自带 `evidence: docId[]`；运行时检查这些文档是否已出现在检索结果里，缺失的用 `searchKb(docId 限定)` **定向取证**。这样保证「每条高风险结论都有对应引用」，而不是指望第一次模糊检索就撞对。
3. **失败驱动的降级**：规划失败 → 标准流水线；生成失败 → 规则合成；证据为空 → 保守回答。每一次降级都会以 `note` 事件显式告知用户，不静默降质。

**工具设计原则**：8 个工具全部是**确定性函数**（`lib/tools/index.ts`），内部不含任何自然语言生成——避免「用模型判断模型」的循环，也让工具可以原样暴露给 MCP。

`lab_assess` 内含 14 类临床规则，例如：

```
IF metformin AND eGFR < 30        → 高风险：停用（乳酸酸中毒）
IF metformin AND 30 ≤ eGFR < 45   → 高风险：减量至 ≤1 g/d + 4 周复查
IF glibenclamide AND age ≥ 65     → 高风险：Beers 清单，换用低血糖风险更低的方案
IF estazolam AND diazepam         → 高风险：苯二氮䓬叠加，跌倒/镇静
IF warfarin AND INR > 3           → 高风险：3–7 天复查 + 出血征象观察
IF warfarin AND aspirin           → 高风险：抗凝+抗血小板，核对联用指征
IF NSAID AND eGFR < 60            → 高风险：停用口服 NSAID
IF NSAID AND ACEI/ARB AND 利尿剂   → 高风险：三联打击，3–7 天复查肌酐
IF ACEI/ARB AND 螺内酯 AND K ≥ 5.5 → 高风险：当日复查血钾 + 心电图
IF digoxin AND eGFR < 50          → 中风险：减量 + 查浓度
IF clopidogrel AND omeprazole     → 中风险：换用泮托拉唑
IF simvastatin AND clarithromycin → 高风险：暂停他汀
IF Hb < 110 AND 抗凝/抗血小板       → 中风险：查大便隐血，排除慢性失血
IF 用药数 ≥ 5                     → 提示：执行用药重整流程
```

### 4.3 RAG 技术应用（6%）

**分块策略**（`lib/rag/index.ts::chunkDocument`）
知识库文档采用 `frontmatter + ## 小节` 结构；按二级标题切分语义块，短于 60 字的残块并入上一块，避免「标题单独成块」的碎片化。块 id 形如 `kb-beers-elderly#2`，本身即证据坐标。

**双路召回**

| 路 | 实现 | 优势 | 局限 |
| --- | --- | --- | --- |
| 稀疏 BM25 | k1=1.5, b=0.75，中文按**相邻二元组**切词 | 术语精确命中强（「华法林」「血钾」「三个 30 秒」） | 无同义扩展 |
| 稠密向量 | 384 维 **signed hashing trick**（FNV-1a 双哈希定位维度与符号），L2 归一化 | 零依赖、确定性、可离线；近似语义召回 | 分辨率低于预训练模型 |

**融合**：RRF（k=60）取两路倒数排名相加，抑制单路异常高分；再叠加**术语重排**——query token 命中「标题 / 小节名 / 标签」每词 +0.05、上限 0.2。医疗检索中「标题命中术语」比语义漂移更可信，这条先验必须显式编码。

最终得分：`score = 0.5·BM25_norm + 0.35·vector + 0.15·RRF_norm + rerank`，clamp 到 [0,1]，每项明细随命中返回并显示在证据面板。

**引用治理**

- 生成阶段要求 `[n]`；`verifyCitations()` 逐条校验编号是否落在本次命中范围内；
- 非法编号计入审计（`invalidIds`）并降低置信度 0.1；
- `guardOutput()` 检测「有剂量数字但无任何引用」→ strict 模式下追加「须由医师核定」提示并告警。

**领域同义词扩展（口语 → 术语）**

本项目的稠密向量是词形投影，**不具备预训练模型的同义泛化能力**——「心慌」和「心悸」在向量空间里几乎无关。而基层用户的真实说法恰恰全是口语：腿肿、睡不着、心里发慌、拉的屎是黑的。

所以加了一层显式归一化（`data/synonyms.json`，18 组，200+ 表述）：命中同组任一词，就把整组术语并入检索。**关键设计是分工**——扩展词只进稠密路（负责泛化），BM25 仍只用原话（负责精确）。早前一版把扩展词也塞进 BM25，「心衰 布洛芬」这类精确提问被「止痛药 / NSAID / 双氯芬酸」一大串同义词稀释，Hit@3 从 0.929 跌到 0.857；改为分工后精确性完全恢复，泛化收益保留。

**评测**（可复现，`npm run eval:rag`）

探针分两类，分开统计——把两类混在一起平均会掩盖一个事实：通用检索在术语上很强、在口语上很弱，而后者才是真实用户。

| 探针类别 | 条数 | Hit@1 | Hit@3 | MRR |
| --- | --- | --- | --- | --- |
| 术语型（医生/药师问法） | 14 | 10（0.714） | 13（0.929） | 0.836 |
| **口语型（老人/家属原话，同义词扩展开）** | 7 | **5（0.714）** | 5（0.714） | **0.743** |
| 口语型（同义词扩展**关**，基线） | 7 | 3（**0.429**） | 5（0.714） | 0.524 |
| 合计（开 / 关） | 21 | **0.714 / 0.619** | 0.857 / 0.857 | **0.805 / 0.732** |

`RAG_SYNONYMS=off npm run eval:rag` 可复现基线。结论写清楚：**同义词扩展把口语提问的 Hit@1 从 0.429 提到 0.714，而术语型指标一条没退**——这是本项目在"没有预训练嵌入模型"约束下，对语义泛化问题给出的工程答案。

术语型未命中的 1 条为「艾司唑仑 + 地西泮 + 摔倒」，首位返回同主题的《老年人潜在不适当用药》而非《药物相关跌倒风险》，两者证据互补，不影响结论。

评测接口为 `POST /api/kb/search`，与线上检索走同一条代码路径，不存在「评测专用实现」。

**为什么不上向量数据库（必须能答的问题）**
本作品知识库为百级分块，内存 BM25 + 向量扫描 < 5ms；引入外部向量库会带来：进程依赖、索引同步、部署失败面、评测环境不可复现。生产化时替换点只有一个函数——`lib/rag/embed.ts::embed()`，检索层与 Agent 层零改动。

### 4.4 多模态能力（5%）

| 模态 | 实现 | 关键工程细节 |
| --- | --- | --- |
| **图像** | 药盒/处方拍照 → `POST /api/vision` → 视觉模型 → **名称归一化** | 模型常输出「拜阿司匹灵」「芬必得」等商品名，必须经 `findDrug()` / `extractDrugs()` 映射回 `drugId`，否则无法参与相互作用计算。未匹配项显式标「未匹配」，不静默放过 |
| **语音输入** | Web Speech API（`zh-CN`），实时回填输入框 | 不支持时给出明确降级提示，不假装可用 |
| **语音输出** | `speechSynthesis`，0.92 倍速，播报前剥离 Markdown 符号与引用编号 | 适老化：语速、去符号、400 字截断 |
| **文本/文档** | 处方 OCR 文本或手工粘贴 → 同一套 `extractDrugs()` 抽取 | 别名表覆盖 29 种药的商品名与俗名 |

**融合方式是「归一化后统一进入同一推理管线」**：不论图片、语音还是文本，最终都变成「患者 + 药物 id 列表 + 主诉」，下游工具无需感知模态差异。这是多模态在工程上真正落地的形态，而不是并列堆三个 API。

### 4.5 AI 安全与可控性（4%）

四道闸门（`lib/safety/index.ts`）：

1. **输入侧**
   - 11 条红旗症状规则（胸痛、黑便呕血、卒中征象、低血糖昏迷、跌倒后头伤、INR 过高伴出血、高钾、AKI、高血压急症、过敏反应、心理危机），命中 emergency 即 `level=block` + `forceReferral=true`，系统提示会把「立即就医」顶到回答最前。
   - PII 脱敏：手机号、身份证、银行卡、邮箱在进入模型前掩码，`sanitizedText` 是唯一进入推理的文本。
2. **过程侧**：工具白名单（未知工具直接跳过并记 `step.skipped`）、`AGENT_MAX_STEPS` 步数上限、请求体长度上限、单次运行超时。
3. **输出侧**：诊断断言改写（`确诊为/就是/肯定是` → `可能涉及`）、绝对化表述拦截、弱化就医表述拦截、剂量无引用拦截、引用合法性校验。
4. **事后**：`logs/runs/{id}.json`（完整轨迹）+ `logs/audit.jsonl`（结构化摘要），`/safety` 页面可视化，`npm run audit:report` 生成 Markdown 汇总。审计里的安全等级取**输入闸门与输出闸门中更严的一档**（`finalLevel`）——只取输出侧会把「命中红旗、回答被前置就医提示」的运行记成 `ok`，那样「强制转诊率」这类质量指标就永远是假的。

**可解释性的三个落点**（评委最容易感知）：
- 回答里的 `[n]` 是可点击徽标，点开即原文 + 四项打分；
- 右侧轨迹显示每步耗时与工具入参；
- `/trace/[runId]` 完整回放，答辩时可现场点开任意一次历史运行。

### 4.6 MCP / 工具集成（4%）

`mcp/server.mjs` 使用官方 SDK（`@modelcontextprotocol/sdk`）实现 stdio 传输的 MCP Server，暴露 `list_patients`、`check_interaction`、`lab_assess`、`search_kb`、`build_med_plan`。

架构上刻意做了**协议层与实现层分离**：MCP Server 只处理 `tools/list`、`tools/call`，实际计算通过 HTTP 桥调用 `POST /api/mcp`（内部复用 `TOOLS` 注册表）。收益：

- 工具实现只有一份，端内 Agent 与外部 Agent 行为严格一致，不会出现「两套逻辑两套结论」；
- MCP Server 可作为独立进程挂到 Claude Desktop / Cursor；
- 未来把工具层拆成独立微服务时，只需改桥接地址。

## 5 核心功能实现

### 5.1 Agent 运行时骨架

```ts
// lib/agent/runtime.ts（节选）
export async function runAgent({ patientId, question, mode, emit }: RunParams) {
  const safety = await screenInput(question, patient);        // ① 输入闸门
  if (safety.flags.length) emit({ type: 'safety', ...safety });

  let steps = mockPlan(question, ctx, safety.forceReferral); // ② 规划（规则基线）
  if (mode === 'llm') steps = await planWithLlm(...) ?? steps; //  LLM 失败自动回退

  emit({ type: 'plan', steps });
  for (const step of steps) await execStep(step, ctx, state, emit); // ③ 工具编排

  await pinEvidence(findings, state, emit);                  // ④ 证据锚定
  const answer = mode === 'llm' ? await generateWithLlm(...) : composeMockAnswer(...); // ⑤ 生成
  const guarded = guardOutput(answer, state.evidence);        // ⑥ 输出闸门
  await saveRun(run); await appendAudit(...);                // ⑦ 留痕
}
```

### 5.2 证据锚定（作品的关键设计之一）

普通 RAG 是「先检索、后生成」，检索质量决定一切。本作品增加了一步反向校验：

```ts
const missingDocs = findings
  .filter((f) => f.level !== 'info')
  .flatMap((f) => f.evidence)
  .filter((docId) => !state.evidence.some((h) => h.docId === docId));

for (const docId of missingDocs.slice(0, 6)) {
  const hit = await searchKb(`证据锚定 ${docId}`, { docIds: [docId], topK: 1 });
  if (hit[0]) pinned.push(hit[0]);
}
```

即：**由风险发现倒逼取证**。这样即使初始检索式没命中，高风险结论也一定拿得到原文，引用覆盖率从「看运气」变成「有保证」。

### 5.3 冲突图谱（手写 SVG）

`components/console/ConflictGraph.tsx`：N 个药物节点按角度均分排成环，相互作用画成贝塞尔直线；高风险连线用 `stroke-dasharray` + `animate-trace-dash` 做流动效果吸引注意；每个节点带透明加粗命中区（12px）便于触屏点击；节点颜色区分医嘱药与非医嘱自购药。

选择手写而非图表库：约 150 行、零体积、可直接注入无障碍标签与键盘交互，且环形布局与「药物两两关系」的语义天然吻合。

### 5.4 MiniMarkdown 渲染器

`components/MiniMarkdown.tsx`：按行解析 `###` 标题、有序/无序列表、引用块，行内解析 `**加粗**`、`` `代码` ``、`[n]` 引用。`[n]` 渲染为按钮，点击回调把对应证据块设为选中并滚动定位——这是「结论 ↔ 证据」双向导航的实现基础。

### 5.5 SSE 消费与增量渲染

`lib/store/useConsoleStore.ts` 用 `TextDecoder` + `\n\n` 分帧，`applyEvent` 做 reducer 式分发。关键点：

- token 事件**只追加到最后一条消息**，避免全量列表重渲染；
- `tool_result` 按 id 回填到对应卡片，不重建数组结构；
- 失败与中断都有兜底：网络异常时消息标记 `streaming:false` 并给出可读错误。

### 5.6 适老化与可访问性

- 大字模式：`html[data-bigtext='true'] { font-size: 18.5px }`，全站 rem 缩放，组件零改动；
- 焦点可见：全局 `:focus-visible` 2px outline；
- 动效尊重 `prefers-reduced-motion`；
- 流式区域使用 `aria-live` 语义（消息容器），按钮均有 `aria-pressed` / `title`。

## 8 总结与展望

### 8.1 完成了什么

- 一个可完整运行、可复现、可审计的用药安全 Agent：7 步工作流、8 个确定性工具、14 类临床规则、17 篇知识库、21 条相互作用规则、11 条红旗规则。
- 一条从「多模态采集」到「家属可执行通知」的闭环，而不只是问答。
- 一套把 AI 过程变成产品界面的交互范式：冲突图谱 + 三栏诊台 + 决策轨迹回放。
- 一份工程上诚实的取舍清单：每一处「不用某个库」都有可辩护的理由。

### 8.2 明确的短板

1. **知识库规模有限**（17 篇、百级分块）：足以支撑演示与规则验证，但不足以覆盖真实处方全集。改进：接入国家药品说明书数据库、Beers/STOPP 标准全文，分块量提升到万级后引入 pgvector + 真实 embedding，接口已隔离。
2. **缺少真实临床验证**：规则依据公开资料整理，未经药师双盲复核。改进：与附属医院药学部和基层卫生院做 30–50 例回顾性对照，统计「高风险组合识别率 / 建议采纳率」。
3. **多模态依赖外部视觉 API**：无 Key 时只能返回演示识别结果（UI 已显式标注）。改进：接入 PaddleOCR-Web / ONNX Runtime Web 做端侧文字识别，先 OCR 再匹配药物库，可完全离线。
4. **未做多轮长期记忆**：当前每轮独立规划。改进：引入会话级「已知事实」缓存（患者已确认的用药变更、上次随访结论），减少重复提问。

### 8.3 展望

- **临床落地路径**：以「村医助手」形态嵌入县域医共体，输出结构化用药重整单，与家庭医生签约随访系统对接。
- **端云协同**：把检索与规则引擎放到端侧（IndexedDB + ONNX/WASM），仅把需要大模型的部分上云，兼顾隐私与成本。
- **从辅助到质控**：把审计日志变成基层用药质量指标（高风险闭环率、7 天随访完成率），支撑区域卫生健康部门的质控考核。
