## 二、逐维度展开

### 1. AI 技术深度（35%，自评 91.1）

六项能力不是"点状堆料"，而是分层：模型层（`lib/llm/provider.ts`）只负责"把话说出来"，工具层（`lib/tools/index.ts`）负责"下判断"，安全层（`lib/safety/index.ts`）负责"拦住不该说的"，运行层（`lib/agent/runtime.ts`）负责把三者按 7 步串起来并落盘。

- 大模型集成：统一走 OpenAI 兼容 `/chat/completions`，内置 openai/deepseek/zhipu/qwen/anthropic 五套预设（`provider.ts:20-34`），规划阶段用 `response_format: json_object` 拿结构化计划，生成阶段用 SSE 逐 token 流式，并请求 `include_usage`。2026-11-17 最新一轮 DeepSeek 3/3 最终 LLM 成功，无降级，平均 12322 ms，Token usage 覆盖 3/3；此前 9 次降级记录继续保留，累计 12 次的历史汇总可复核。
- Agent 工作流：`mockPlan` 生成 s1–s7 七步（`runtime.ts:78-123`），`normalizeLlmPlan` 对模型输出做防御式解析——步数不足回退、模型"忘记"守门则强制补一步（`runtime.ts:144-148`）。实测一次运行 6 次工具调用、1.1–2.1 s 完成、置信度 0.89–0.93。
- 多轮与自检：明确追问只继承最近一轮用户主题，历史先脱敏并限长；语境消解后重新执行红旗筛查。回答结束后再做引用合法性、高风险证据覆盖与来源追溯检查，右栏展示逐项结果。
- RAG：原话 BM25、受限同义词 BM25 与哈希向量参与 RRF，单条证据带 `scoreBreakdown` 四项打分（`lib/rag/index.ts`）。实测 63 条项目自标注探针 **Hit@1/3/5 0.889/1.000/1.000，MRR@5 0.939，Recall@5 0.955，nDCG@5 0.910**；6 条多相关查询尚未召回齐全部标注文档，标签仍待独立复核。
- 多模态与 MCP：视觉识别后强制做 `drugId` 归一化（`app/api/vision/route.ts:60-82`）；5 个能力经 MCP stdio 外化，实现层仍在 `app/api/mcp/route.ts:43` 这一处。
- 主要扣分依据：知识库规模有限（59 块）、检索标签缺少独立一致性检验、具体建议尚未完成指南段落映射，以及多模态依赖外部模型；因此不把工程指标解释为临床有效性。

### 2. 创新性（25%，自评 92.2）

创新不在"用了大模型"，而在三个"别人不做但用户真的需要"的地方，且三处都能现场点开。

- 冲突图谱（`ConflictGraph.tsx`）：7 种药排环、21 条规则画线，红色虚线做流动动画，节点色区分医嘱/非医嘱，点击展开机制与处置。手写 SVG 约 180 行，零图表库，还带 `role="img"` 与 `aria-label`。
- 证据徽标（`MiniMarkdown.tsx:41-52`）：回答正文里的 `[n]` 渲染成真按钮，点击触发 `selectChunk` → 右栏自动切到证据并 `scrollIntoView`（`InsightPanel.tsx:39-44`）。这把"引用"从装饰变成了导航。
- 双引擎契约（`runtime.ts:38-43` 注释与实现）：有 Key 时是自主规划 Agent，无 Key 时是确定性流水线，两者共用同一套工具、检索、安全管线，所以"降级"不会改变产品行为——这是能在答辩现场自证的设计。

创新项的技术含量还有一处容易被忽略：证据锚定（`runtime.ts:472-488`）。高风险发现若没被常规检索覆盖，运行时会用它的 `evidence` docId 做定向取证，把缺失的原文补进证据链，而不是"没检到就算了"。

### 3. 前端工程质量（10%，自评 94）

工程分不是"好看"，是"可维护 + 可验证"。六条硬证据：

- 类型：`tsconfig.json` 开 `"strict": true`，`npm run typecheck`（`tsc --noEmit`）实测 0 错误。全链路共用 `lib/types.ts` 一套类型——`AgentRun`、`SseEvent`、`KbHit`、`SafetyReport` 从服务端事件到 UI 渲染到审计落盘是同一个结构。
- 状态：`lib/store/useConsoleStore.ts` 用单一 `applyEvent` reducer 消费全部事件；流式 token 先给出响应感，结束时由 `answer_final` 用守门后的文本替换草稿，保证展示内容与落盘回答一致。
- 服务端优先：诊台在服务端把 4 位患者的完整数据包一次组装下发（`app/console/page.tsx:14-17`、`lib/data.ts:112-130`），切患者零请求。
- 依赖纪律：不装 react-markdown（自研 128 行渲染器）、不装图表库（手写 SVG）、不装 AI SDK（自研 SSE，`app/api/chat/route.ts` 用原生 `ReadableStream`），首屏无重型包。
- **测试与 CI**：本轮记录 `npm test` 72/72 通过；当前提交前复核的 smoke 4/4 通过；`.github/workflows/ci.yml` 配置 `typecheck → lint → test → build`。流式解析新增回归，确保上游在 `[DONE]` 前发送的 usage 不会丢失。这些检查覆盖工程行为，不覆盖临床准确性。
- **可验证的界面质量**：`npm run audit:ui`（2 视口 × 5 个关键页面：运行时异常 / 横向溢出 / 可访问名称 / 大字模式）+ `npm run audit:review`（逐元素实测对比度、`Tab` 走查焦点环、24px 点击区、320px 重排，发现任一问题即非零退出）。扩展到轨迹页与真实暗色主题后，又捕获并修复了轨迹页 320px 溢出、19 个小点击区和主题切换过渡态误测；当前四项全部归零（`docs/评审-界面.md`）。

### 4. 实用性（10%，自评 88）

## 三、短板与改进计划

> 这一节按答辩要求"诚实列弱项"，每条都给出可执行的下一版动作。

**弱项 1：知识库规模小，来源映射与专业复核未完成。**
现状：`data/kb/` 17 篇、59 个分块、平均 110 字（实测 `/api/kb/search`）；`data/kb/sources.json` 已登记候选文献与 DOI，其中 Crossref 只核验书目元数据，未完成“具体建议—原文段落”映射；一条演示知识未登记外部来源。检索评测扩展至 63 条多相关性探针，但由项目作者自标，没有独立一致性检验；临床上“该不该停这个药”没有专家标注。
风险：评委追问"这条规则出自哪一版指南"时只能指到自写文档；"检索命中"容易被误当成"临床正确"。
改进：一，邀请药师逐条审核知识条目、阈值与处置建议并记录指南版本/原文段落；二，邀请独立标注者复核检索相关文档集合，记录一致性并锁定测试集；三，完成专业审核前，系统仅用于工程演示，不用于患者决策。

**弱项 2：检索式构造曾被上下文稀释（已修复，当前仍有多文档召回缺口）。**
原现状：规则引擎把"用户问题 + 主诉 + 全部药名 + 全部诊断"一次性拼成检索式，主题被药名带偏。实测证据：p-001 的问题关于出血，三条最高分证据却全是 `kb-diabetes-basics`（1.00 / 1.00 / 0.9478）。
**已修复**：新增 `buildRetrievalQuery()`（`lib/agent/runtime.ts`）——以「用户原话 + 主诉」为主体，只有当问题里没提到任何药名（含商品名/俗名，按 `drugs.json` 别名判断）时才补最多 3 个药名；`topK` 6 → 8，缺失证据交给证据锚定按 docId 定向补齐。同一问题的修复前后对比：糖尿病文档全部退出前三，首位变为 `kb-antiplatelet`（1.000）、`kb-nsaid-anticoag`（0.956）、`kb-anticoag-bleeding`（0.940）；引用数 9 → 11。
当前：新增口语变体回归后发现哈希向量无法稳定召回“心里发慌、腿也肿”对应的所有多相关文档；已将人工同义词加入受限 BM25 补充路，并过滤零分 BM25 的 RRF 候选。实测 63 条探针 Hit@3 = 1.000、Recall@5 = 0.955，但 6 条多相关查询仍未召回齐所有标签。
后续：独立复核这 6 条查询的相关文档标签，避免对自标注集过拟合；保留一份锁定的回归集并持续记录版本化指标。

**弱项 3：多模态依赖外部视觉 API，且缺本地方案与图片隐私处理。**
现状：未配置 Key 时返回显式标记的 `provider: 'mock'`；只配置文本模型时返回 `VISION_MODEL_NOT_CONFIGURED`，不会把 DeepSeek Chat 冒充成视觉模型。本轮已加入图片确认、浏览器重编码去元数据、服务端尺寸/签名校验，并建立 4 张开放许可原图派生的 36 张鲁棒性样本。配置真实视觉模型时，图片仍会发给该外部服务；当前没有真实视觉准确率。
风险：断网或额度耗尽时多模态降级为演示模式；当前没有离线 OCR，也没有逐药勾选确认，识别结果需要用户检查后主动点击加入核对。
改进：加入本地 OCR（Tesseract.js 或 PaddleOCR wasm）先提取文本，再交给药物库匹配，视觉模型只用于纠错；识别结果增加逐药确认，未经确认的药不进入风险计算。真实临床使用前还需评估模型供应商的数据处理条款。

**弱项 4：工程化底座偏"比赛形态"（安全等级聚合缺陷已修复）。**
现状：无数据库（`lib/data.ts` 顶部注释说明是刻意选择），轨迹落 `logs/runs/*.json`（`lib/agent/store.ts`），内存里最多留 60 条；审计是 JSONL 追加写（`lib/safety/index.ts`），可被本地篡改、无签名、无租户隔离。
**已修复**：原先落盘用的是 `guarded.level`（输出守门等级），会覆盖输入侧红旗的 `block`，导致命中"可疑上消化道出血"的运行在审计里记为 `ok`。现改为 `finalLevel = max(输入等级, 输出等级)`（`ok < notice < block`）。修复后 `npm run audit:report`：`安全等级：{ ok: 10, block: 3, notice: 2 }`。
后续：一，审计行单列 `inputLevel / outputLevel` 两个字段，便于质量分析；二，引入 Postgres + pgvector（`patients / meds / runs / audit` 四表，`embed()` 接口不变），审计行加 `prev_hash` 形成链式哈希；三，租户维度只加 `org_id` 过滤，不动业务逻辑。

**弱项 5：交付一致性与环境可复现性有瑕疵（数字不一致已修正）。**
现状：实测发现三处，已处理两处。一，`data/drugs.json` 实际 **29** 条，README / 技术文档 / 依据页原先写"28 种"——**已统一改为 29**；二，本机曾出现 `node_modules/.bin` 缺失、`npm run dev` 报 `'next' 不是内部或外部命令`，确认与"npm install 尚未完成时并发执行"有关，重装后 `npm run dev` / `npm start` 均正常；三，`next build` 在本机偶发失败（`Invariant: no direct app page entry found for /_not-found`、`.nft.json` ENOENT），间隔重试即通过，已用 `outputFileTracingRoot` 固定工作区根目录缓解，并写入 `docs/verify.md` 的"已知限制"。
风险：评委按 README 复现时若恰好踩到环境噪声，会影响"可复现性"印象。
后续：一，README 加一行"所有数量以数据文件为准"；二，交付前跑一遍干净复现：`rm -rf node_modules .next && npm ci && npm run dev`，写进提交清单；三，README 的"快速开始"补一条预热提示（先访问 `/evidence` 触发检索路由编译，再跑 `npm run eval:rag`）；四，`.nvmrc` 与实际验证过的 Node 版本对齐（实测 Node 24.11.1 / npm 11.6.2）。
