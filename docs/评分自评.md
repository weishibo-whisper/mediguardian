## 二、逐维度展开

### 1. AI 技术深度（35%，自评 87.9）

六项能力不是"点状堆料"，而是分层：模型层（`lib/llm/provider.ts`）只负责"把话说出来"，工具层（`lib/tools/index.ts`）负责"下判断"，安全层（`lib/safety/index.ts`）负责"拦住不该说的"，运行层（`lib/agent/runtime.ts`）负责把三者按 7 步串起来并落盘。

- 大模型集成：统一走 OpenAI 兼容 `/chat/completions`，内置 openai/deepseek/zhipu/qwen/anthropic 五套预设（`provider.ts:20-34`），规划阶段用 `response_format: json_object` 拿结构化计划，生成阶段用 SSE 逐 token 流式，并开启 `include_usage` 回传真实 token 用量（`provider.ts:130`）。
- Agent 工作流：`mockPlan` 生成 s1–s7 七步（`runtime.ts:78-123`），`normalizeLlmPlan` 对模型输出做防御式解析——步数不足回退、模型"忘记"守门则强制补一步（`runtime.ts:144-148`）。实测一次运行 6 次工具调用、1.1–2.1 s 完成、置信度 0.89–0.93。
- RAG：双路召回 + RRF + 重排，单条证据带 `scoreBreakdown` 四项打分（`lib/rag/index.ts:202-218`）。实测 14 条探针 **Hit@1 0.714 / Hit@3 0.929 / MRR 0.836**，唯一漏前三是"格列本脲"一条（详见第三节弱项）。
- 多模态与 MCP：视觉识别后强制做 `drugId` 归一化（`app/api/vision/route.ts:60-82`）；5 个能力经 MCP stdio 外化，实现层仍在 `app/api/mcp/route.ts:43` 这一处。
- 为什么给 87.9 而不是更高：扣在知识库规模（59 块、14 条探针）与多模态外部依赖上。

### 2. 创新性（25%，自评 90.2）

创新不在"用了大模型"，而在三个"别人不做但用户真的需要"的地方，且三处都能现场点开。

- 冲突图谱（`ConflictGraph.tsx`）：7 种药排环、21 条规则画线，红色虚线做流动动画，节点色区分医嘱/非医嘱，点击展开机制与处置。手写 SVG 约 180 行，零图表库，还带 `role="img"` 与 `aria-label`。
- 证据徽标（`MiniMarkdown.tsx:41-52`）：回答正文里的 `[n]` 渲染成真按钮，点击触发 `selectChunk` → 右栏自动切到证据并 `scrollIntoView`（`InsightPanel.tsx:39-44`）。这把"引用"从装饰变成了导航。
- 双引擎契约（`runtime.ts:38-43` 注释与实现）：有 Key 时是自主规划 Agent，无 Key 时是确定性流水线，两者共用同一套工具、检索、安全管线，所以"降级"不会改变产品行为——这是能在答辩现场自证的设计。

创新项的技术含量还有一处容易被忽略：证据锚定（`runtime.ts:472-488`）。高风险发现若没被常规检索覆盖，运行时会用它的 `evidence` docId 做定向取证，把缺失的原文补进证据链，而不是"没检到就算了"。

### 3. 前端工程质量（10%，自评 94）

工程分不是"好看"，是"可维护 + 可验证"。六条硬证据：

- 类型：`tsconfig.json` 开 `"strict": true`，`npm run typecheck`（`tsc --noEmit`）实测 0 错误。全链路共用 `lib/types.ts` 一套类型——`AgentRun`、`SseEvent`、`KbHit`、`SafetyReport` 从服务端事件到 UI 渲染到审计落盘是同一个结构（`lib/types.ts:227-247` 定义 12 种 SSE 事件）。
- 状态：`lib/store/useConsoleStore.ts:97-190` 用单一 `applyEvent` reducer 消费全部事件，组件不碰 fetch 细节；`live` 与 `messages` 分离，流式 token 只追加到最后一条消息，避免全量重渲染。
- 服务端优先：诊台在服务端把 4 位患者的完整数据包一次组装下发（`app/console/page.tsx:14-17`、`lib/data.ts:112-130`），切患者零请求。
- 依赖纪律：不装 react-markdown（自研 128 行渲染器）、不装图表库（手写 SVG）、不装 AI SDK（自研 SSE，`app/api/chat/route.ts` 用原生 `ReadableStream`），首屏无重型包。
- **测试与 CI**：`npm test`（vitest，41 个用例：检索 12 / 工具 16 / 安全 13）全通过，且测试文件本身也在 `tsc --noEmit` 范围内；`.github/workflows/ci.yml` 每次 push 跑 `typecheck → lint → test → build` 四关。
- **可验证的界面质量**：`npm run audit:ui`（2 视口 × 4 页面：运行时异常 / 横向溢出 / 可访问名称 / 大字模式）+ `npm run audit:review`（逐元素实测对比度、`Tab` 走查焦点环、24px 点击区、320px 重排）。首轮实测查出对比度 60 处不合格（最差 2.49:1）、点击区 38 处过小、2 个页面 320px 横向滚动；令牌级修复后四项全部归零（`docs/评审-界面.md`）。

### 4. 实用性（10%，自评 86）

判断标准是"村医看完能不能直接用"。8 个工具的输出都是可执行物：`build_med_plan` 产出"保留/调整/停用/复查/教育"五段式（`lib/tools/index.ts:426-531`），`make_referral` 产出带"携带资料 + 交接要点"的转诊单（`lib/tools/index.ts:554-589`），`notify_family` 产出可直接粘贴到微信的口语化通知（`lib/tools/index.ts:594-613`），`speak` 产出剥掉 Markdown 符号、限 300 字的播报稿（`lib/tools/index.ts:618-633`）。

扣分点在真实场景的"前半段"：药盒拍照识别依赖外部视觉模型，实际药盒的通用名/规格识别准确率我们还没有真实样本量的数据；名单导入、随访记录回写也还没做。所以 86 而不是 92。

### 5. 用户体验（10%，自评 88）

体验的核心主张是"每一步都有反馈"，包括坏消息：

- 过程可见：规划步骤逐条出现、工具卡显示毫秒数、`<details>` 可展开入参（`InsightPanel.tsx:192-213`）、置信度条按 0.75/0.5 分三色（`InsightPanel.tsx:260-274`）。
- 风险可见：命中红旗症状时，输入区上方直接弹红色横幅"本回答以立即就医为第一优先级"（`ChatPanel.tsx:185-192`），不等回答生成完。
- 失败可见：模型降级用黄色 `note` 明说是"降级"而非报错（`runtime.ts:534-541`）；未匹配的药物标"未匹配"而不是猜（`app/api/vision/route.ts:79-82`）。
- 适老化：大字模式整站 `font-size: 18.5px` 重排（`globals.css:57-59`，实测 4 个页面均生效并跨页持久化）、`prefers-reduced-motion` 全局降动效（`globals.css:194-203`）、`focus-visible` 焦点环（`globals.css:80-84`，`Tab` 走查 0 处缺失），语音输入不支持时给替代文案而不是静默失败（`ChatPanel.tsx:83-87`）。
- 对比度：全部文字按渲染后颜色实测（双主题 × 4 页 125 种样式），最差组合 4.70:1，优于 WCAG AA 的 4.5:1；主按钮深色主题曾只有 2.49:1，已通过 `--accent-solid` 拆令牌修到 5.47:1。
- 点击区与重排：指针目标全部 ≥ 24×24px；320px 视口无横向滚动（`app/safety/page.tsx:140` 的 `min-w-0`、`app/arch/page.tsx:160` 的滚动容器）。

未给更高的原因：三栏布局在 1280px 以下会收缩，移动端主要靠横向导航，村医手机端的完整流程尚未验证。

### 6. 社会价值与商业潜力（10%，自评 82）

价值侧站得住：可预防的用药伤害集中在消化道出血、低血糖、跌倒、急性肾损伤四类，而这四类恰好对应 `lab_assess` 的规则分支（`lib/tools/index.ts:130-363`）与 11 条红旗（`data/redflags.json`）。产品定位是"辅助 + 可追溯"，不做诊断、不给处方，责任边界清楚（`lib/safety/index.ts:16-17` 的免责声明与 `prompts.ts:17-30` 的角色约束）。

商业侧只有纸面路径，没有付费验证：无 Key 可全链路运行（`provider.ts:62`）意味着零模型预算的村卫生室也能上线；工具层通过 MCP 外化（`mcp/server.mjs` + `app/api/mcp/route.ts`）意味着可以嵌进既有 HIS。但试点机构、单价、获客路径都还没有数据，所以给 82。

## 三、短板与改进计划

> 这一节按答辩要求"诚实列弱项"，每条都给出可执行的下一版动作。

**弱项 1：知识库规模小、来源层级浅，且没有真实临床验证。**
现状：`data/kb/` 17 篇、59 个分块、平均 110 字（实测 `/api/kb/search` 的 `docCount/chunkCount/avgChunkLen`）；条目是"按公开说明书与 Beers 标准整理改写"，没有指南原文、版本号与生效年份、也没有 DOI/链接。评测只有 14 条探针，标准答案由我们自己设定（`scripts/eval-retrieval.mjs:17-32`），属于自洽性验证；临床上"该不该停这个药"没有专家标注。
风险：评委追问"这条规则出自哪一版指南"时只能指到自写文档；"检索命中"容易被误当成"临床正确"。
改进：一，给每篇 kb 补 frontmatter `source_title / source_org / year / url / level`（`lib/rag/index.ts:37-57` 的 `parseFrontmatter` 已支持 key: value，解析器不用改），优先补齐 Beers 2023、中国老年人潜在不适当用药目录、二甲双胍与华法林说明书、房颤抗凝指南、CKD 分期指南；二，探针扩到 60 条并覆盖易混对（"牙龈出血" vs "牙龈增生"、"低钠盐" vs "低钠血症"），标准答案改为"可接受文档集合"；三，请 2 名执业药师对 30 个合成病例盲评，记录"建议采纳率 / 危险建议率"。

**弱项 2：检索式构造曾被上下文稀释（已修复，残留一处文档边界问题）。**
原现状：规则引擎把"用户问题 + 主诉 + 全部药名 + 全部诊断"一次性拼成检索式，主题被药名带偏。实测证据：p-001 的问题关于出血，三条最高分证据却全是 `kb-diabetes-basics`（1.00 / 1.00 / 0.9478）。
**已修复**：新增 `buildRetrievalQuery()`（`lib/agent/runtime.ts`）——以「用户原话 + 主诉」为主体，只有当问题里没提到任何药名（含商品名/俗名，按 `drugs.json` 别名判断）时才补最多 3 个药名；`topK` 6 → 8，缺失证据交给证据锚定按 docId 定向补齐。同一问题的修复前后对比：糖尿病文档全部退出前三，首位变为 `kb-antiplatelet`（1.000）、`kb-nsaid-anticoag`（0.956）、`kb-anticoag-bleeding`（0.940）；引用数 9 → 11。
残留：`格列本脲 老年人 低血糖` 这条探针期望 `kb-beers-elderly`，实际排第 5（Hit@3 因此为 13/14），因为格列本脲的低血糖机制同时写在 `kb-diabetes-basics` 里。
风险：证据面板"最相关的三条文不对题"会削弱可信度——这条风险已通过上面的修复消除大半。
后续：一，主检索也按风险发现拆开（定向取证已具备该能力）；二，给 `searchKb` 增加文档主题加权；三，清理 `kb-beers-elderly` 与 `kb-diabetes-basics` 的交叠段落，形成"一条规则一个归属文档"的约定。

**弱项 3：多模态依赖外部视觉 API，且缺本地方案与图片隐私处理。**
现状：`app/api/vision/route.ts` 在未配置 Key 时返回 `provider: 'mock'` 的演示结果（`route.ts:35-46`），真实识别走 `visionExtract`（`lib/llm/provider.ts:180-212`）；图片上限 4MB（`ChatPanel.tsx:106`）；没有 EXIF 清除。
风险：断网或额度耗尽时多模态直接降级为演示模式；药盒照片可能带定位信息。
改进：一，把 EXIF 剥离与等比压缩放到前端 canvas 预处理（当前只是 `FileReader` 读 base64）；二，加一层"本地 OCR 兜底"（Tesseract.js 或 PaddleOCR wasm）先出原始文本，再交给规则做药名匹配，视觉模型只做纠错；三，识别结果页增加"人工确认"勾选，未确认的药不进入风险计算。

**弱项 4：工程化底座偏"比赛形态"（安全等级聚合缺陷已修复）。**
现状：无数据库（`lib/data.ts` 顶部注释说明是刻意选择），轨迹落 `logs/runs/*.json`（`lib/agent/store.ts`），内存里最多留 60 条；审计是 JSONL 追加写（`lib/safety/index.ts`），可被本地篡改、无签名、无租户隔离。
